# WPS 云同步：值原样上传 + 表间独立上传（需求）

- 状态：**已实现**（2026-10-14 落地，本仓；对应桌面端 3.6.9/3.6.10 的同名落地）
- 触发事故：3.6.22 时期，2026-10-12 21:20 医学院中餐 同步失败并连带阻断后续表
- 相关文档：`docs/WPS-SYNC-RULES.md`（现有规则与安全边界，本需求对其有修改）

---

## 1. 一句话

**顾客怎么填的，表格就怎么上传**；每张表各传各的，一张表出问题不影响其它表上传。

## 2. 背景：这次事故（为什么要这两条）

2026-10-12 21:20 正式同步，医学院中餐 报：

```
[云同步] 医学院中餐 排序后定位不到这些人：mer
```

随后该表被判「写入结果不确定」，同批排在后面的 杭电午餐/东湖晚餐/衣锦晚餐/医学院晚餐
被标为「意图日志阻断，未写入」；21:22 再点同步被「存在未完成/不确定的意图日志，
已阻断本次写入」整体拦下。

根因（已查实，见云端实读数据）：

| 环节 | 事实 |
|---|---|
| 本地排单表 | mer 电话 = `159678999961`（12 位，客户/录入怎么填就是什么） |
| 写端 | `write_cells` 统一用 `opType=formula` 写，12 位数字被金山文档存成**数字** |
| 云端单元格 | `originalCellValue=159678999961`、`numFormat=通用格式`，回读 `cellText` = `1.59679E+11`（科学计数，只剩 6 位有效数字） |
| 人键 | 按回读值算 `('mer','15967911')` ≠ 本地 `('mer','159678999961')` |
| 结果 | 整表排序后要靠回读的「姓名+电话」重新定位每个人 → mer 必然定位不到 → 该表 uncertain → 连带阻断 |

**关键结论：问题不是"电话位数不对"，而是"写进去的值和读回来的值不是同一个东西"。**
因此修改方向不做位数校验、不做号码清洗——那既解决不了根因，也不符合下面第 3 条。

## 3. 需求一：值原样上传（写什么、读什么、显示什么）

1. 本地排单表里客户怎么填，云端就存什么：**不做 11 位/位数校验，不截断，不改写
   （含空格、连字符、`+86`、前导 0 等一律保留原样），也不因为号码形态跳过或拒写任何客户。**
2. 写入与回读必须是同一个值：写进 `159678999961`，回读就要是 `159678999961`
   （或规范化后等价的同一形式）。**不允许因为云端显示格式（科学计数法等）导致回读值变形。**
3. 用「姓名+电话」找人的匹配必须建立在**值本身**上，而不是"显示文本"上。因此：
   - 不再出现「排序后定位不到这些人」；
   - 「云端已有同名的人（电话不同）」这条提醒只在**值真的不同**时出现，不因显示差异误报；
   - 重复同步幂等：第二次同步对同一批人是 no-op，不重复加餐、不多插行。
4. 云端表是给协作者看的：单元格显示要忠实于原值（12 位号码就完整显示 12 位，
   不能显示成 `1.59679E+11`）。
5. 明确不做：不新增电话位数校验/拦截；不"猜"正确号码；不自动改客户填的内容。

## 4. 需求二：表间独立上传（一张表失败不牵连别的表）

1. 一次同步包含多张表时，某张表失败/结果不确定，**其它表继续正常执行、各自记账、各自汇报**。
2. 某张表留下「未完成/不确定」记录时，**只堵这一张表**（该表未核清前自己不许重写，防重复加餐），
   **不得阻断其它任何表的写入**（含其它日期批次）。
3. 汇总与日志要能一眼看出「本次哪几张表成功、哪张表需要人工处理」；
   不允许出现"一张表不确定 → 整批都算失败/未执行"的表述。
4. 同类风险应各自独立暴露：如果其它表也有值回读不一致等问题，各自报各自的，
   不要被第一张表掩盖。
5. 既有安全边界不回退：上传前预览、批次日期校验、协作者 `0` 只读、排序成功后可重跑、
   账本幂等锚点、失败不影响本地排单任务（详见 `docs/WPS-SYNC-RULES.md` 第 6 节）。

## 5. 验收标准（可测）

**A. 值原样上传**

造数据：电话分别取 11 位、12 位、带空格（`159 6789 9961`）、带连字符、`+86` 前缀、
前导 0、超长 15 位等形态，分散在各张表里做一次正式同步。断言：

1. 云端每格读回值与本地一致（同一规范化口径）；
2. 排序后能定位到每个人，不出现「排序后定位不到」；
3. 云端单元格显示不出现科学计数法；
4. 相同数据再同步一次 = no-op（无新增行、无重复加餐）；
5. 预览不出现「同名电话不同」误报（真同名不同号仍要提醒）。

**B. 表间独立上传**

构造一张表必然失败（最直接：复现上面的事故数据），断言：

1. 它之后的表仍然完成上传并报 ok；
2. 下一次同步：失败表继续要求人工核对（它自己仍被保护），其余表正常运行；
3. 失败表核清后可正常重新预览/上传，不受其它表影响。

## 6. 与现状机制的差异（要改什么）—— 落地结果

| 原行为 | 落点 | 已改为 |
|---|---|---|
| 同一批里某表 uncertain 后，后续表被标记 `blocked`、连尝试都不尝试 | `app/wps/executor.py`（原 `stop_after_uncertain`） | **已删除**：逐表 continue；未预期异常也只把该表记成结果未知（`_abort_sheet`），后续表照常执行 |
| 任一张表有未决记录时，启动即整体拒写 | `app/wps/executor.py`（原 `pending_operations()` 全局闸门） | 闸门改为 `journal.blocking_operations(target_date, file_id)`，**按（日期 + 表）设限**：只拒被影响的那一张；仍在恢复流程里能自动核清的历史操作保持原「重新预览」口径 |
| 恢复对账（能自动判定的自动判定） | `app/wps/recovery.py` / `classify_journal_sheet` | 保留，逐表判定不变 |
| 写值被当数字存（`opType=formula`）、回读只取 `cellText` 显示值 | `app/wps/cli.py`（`write_cells` / `read_grid`） | 读优先取 `originalCellValue`（`_cell_text`，显示文本兜底）；新客户电话按文本写（`text_cell_formula`，纯数字前置单引号） |

## 7. 相关代码位置（排查结论，供方案设计参考）

- `app/wps/executor.py:826-837`：排序后重定位与「定位不到」判定。

- 已有先例可对照：`app/ordering/archive.py:60` 注明「电话按文本写，避免 Excel 把

  本需求明确不往云同步链路搬这套校验**）。
