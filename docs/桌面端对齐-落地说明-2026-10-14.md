### 3. D01 ~ D11 核心业务缺陷（桌面端排查记录）

| 编号 | 主题 | 本项目处理 |

| D01 | 多行客户排序后槽位身份错配 | 本项目原本就用**排序辅助列身份 token**定位（比桌面端的地址组更强）；本次补上**地址回读核对**：计划时记 `Change.address_in_sheet`（云端地址原文），排序后逐行比对，对不上 → 整表停写、提示重传。`tests/test_wps_cloud.py::test_排序后地址核对不通过时整表停写` |
| D02 | 补单重跑改变行序 → 旧订单被当新槽位 | 账本按槽位记**订单号**（`orders`）与**物理位置**（`positions`）；规划按订单号把本地行放回槽位（`planner._slots_by_identity`），旧账本按行号配对并补记身份。`test_补单重跑按订单身份配对槽位` |
| D03 | 本地行数减少时丢末尾槽位锚点 | `_ledger_entries` 的 `max_slot` 改 1-based（覆盖旧 `orders`）；账本有身份、本地缺行的槽位留空不压缩。`test_本地行数减少时保留末尾槽位锚点` |

### 4. 闪时送：接口模式平台驳回自动重试（桌面端 v3.6.7 的接口模式部分）

- 平台内部异常驳回（HTTP 200 + `IndexOutOfBoundsException` 等，**确定未建单**，
  依据 2026-10-09 排查与桌面端浏览器模式 102 单实跑）→ **同一单内**自动重试，
  最多 **3 次尝试**（`_API_SUBMIT_ATTEMPTS`），每次尝试重新过提交节流
  (`_SubmitPacer`)，各占一个 `send_seq` / `attempt_id` / 诊断记录。
- **红线不动**：超时/断连/缺 `success` 字段（结果未知）绝不自动重发；业务类拒绝
  （"地址无效"等）不重试；重试等待期间被停止/401/余额拦下时保留"已发出请求"的
  结论，绝不改记「未发送」。落点 `app/ordering/submission.py`
  `_RetryableInternalReject` / `_check_success` / `_submit_tasks_concurrent`。
- 重试用尽后**保持本项目的保守口径**：仍记「技术异常（结果未知）」，进入本地
  记录与「核对并补单」流程（见下方刻意取舍）。

## 二、与桌面端的刻意取舍

1. **不移植"提交前静默 0.5s"**：桌面端为对齐浏览器模式"填完等 0.5s 再点确定"
   而加；本项目提交最小间隔出厂 2.5s（相邻 POST 起点已强制错开），静默只会把
   每单再拖慢 0.5 秒，收益未经证实。
2. **重试用尽后的分类不同**：桌面端记「提交失败」；本项目保持「技术异常/待对账」——
   与既有的 journal 记录、`summary.submission` 计数与「核对并补单」入口相容，
   偏保守一侧（宁可多一次对账，不把可能已落单说成确定失败）。
3. **浏览器模式相关一律不适用**：桌面端 3.6.6 的弹窗内自动重试、`_ui_wait_modal_closed`
   修复、未决日志阻断移除等属于 Playwright 链路，本项目没有浏览器模式
   （未决记录跨运行阻断也已在 3.6.19 下线，见 `docs/SSS-不确定记录处置.md`）。
4. **值原样上传不做号码清洗**（与需求一致）：`159 6789 9961` 与 `159678999961`
   在云端值上仍是两种写法，需要统一时由数据侧处理，程序不猜。
