# 闪时送：部分订单失败、程序重试成功的排查

## 已确认的现场事实（2026-10-08）

原始截图显示：

- 07:33:24，名单共 85 单，配置并发 4 路、读取超时 30 秒。
- 07:33:26，提交前已匹配 80/85 单，缺失 5 单、重复 0 单。
- 07:33:27，本轮实际提交 5 单，耗时 1.1 秒，每单平均 0.7 秒。
- 07:33:44，收尾只读对账仍匹配 0/5 单。
- 第 63 行的弹窗提示 `java.lang.IndexOutOfBoundsException: Index: 0, Size: 0`。

因此不能把 85 当成本轮 POST 次数，也不能凭这张截图认定五单都返回了相同错误。
用户报告网站手动下单及等待一两分钟都未成功，而程序点击单单重试后才看到订单。
现有材料没有首次与重试的原始 HTTP 请求、响应、平台事务记录或成功时刻，不能证明
并发、平台数据、请求差异中的哪一项是这次失败的根因。

提供的 `zcode-2026-10-08.jsonl` 是编码工具的会话运行日志，不是闪时送 HTTP 日志。
以上业务事实来自其关联的原始截图，不来自先前助手的解释。

## 当前代码中已离线复现并修复的问题

1. **内部异常被当成可重发的明确失败。** 原实现只要 `success=false` 带非空
   `message` 或非零 `code` 就清理前置记录，Java 异常也会进入人工重试路径。
   现在技术异常、未知失败、仅有错误码、HTTP 429/全部 5xx 均保持“已发送未知”，
   只做对账，不凭错误文字认定事务已回滚。只有可识别的参数校验拒绝保留重试决策。
2. **跨餐任务标识冲突。** 原标识仅含行号和姓名；午餐、晚餐同名同行会共用
   `task_by_id` 和状态集合，可能把另一餐的成功当作本餐确认，或清掉另一餐的未决记录。
   标识现在包含子表名；客户端 UUID 生成材料未变，历史 journal 仍按原 UUID 核对。
3. **工作线程丢失登录上下文。** `fork()` 原本只复制 token，不复制登录 Session 的
   Cookie 和动态请求头。现在复制它们，但每个 worker 仍有独立 Session/CookieJar，
   不跨线程共享可变会话。
4. **请求头与网页不一致。** 已下载的网页请求拦截器对登录后的建单请求添加
   `terminal: web`。程序已对齐该 HTTP header；它不是 JSON 字段。
   此差异已确认，但没有证据表明它是本次故障的根因。
5. **恢复后的失败状态未清除。** 成功重试或站内对账确认后，当前错误及失败计数
   现在会清除，不再同时报告“已确认”与旧失败。

首次提交与单单重试均复用同一任务 payload；重试使用新的工作线程 Session，且改为
串行 1 路。代码事实不等于现场逐字节请求证据，也不证明串行必然能解决平台异常。
本次没有修改出厂并发，也没有发送真实订单或改写现场配置/journal。

## 新行为与诊断

遇到同类 Java 异常时，不再弹出“可以直接补发”的重试决策。程序先只读对账；
对账仍查不到则保留未决记录，禁止重跑补发。处置走现有管理员面板：先只读核对，
确认站内不存在后带审计解除，而不是删除 journal。参见
[未决记录处置手册](SSS-不确定记录处置.md)。

每次真实提交生成一条脱敏诊断，保存在用户配置目录：

```text
sss-diagnostics/YYYY-MM-DD.jsonl
```

记录包含批次/本地请求标识、餐次/行号、开始时间、耗时、并发配置与提交最小间隔、
分类、HTTP 状态、响应 success/code、技术异常类名以及 payload/实际 HTTP body 摘要。
token 和 Cookie 仅记录使用进程随机密钥生成的上下文摘要，用于同一进程内比较变化；
不保存凭据、姓名、手机号、地址、原始请求体或响应正文。

失败诊断也会进入界面运行日志，日志末尾注明诊断文件位置。
诊断写入失败只给警告，不改变订单结果；防重复仍由提交前 journal 和只读对账负责。

## 2026-10-09 现场：平台建单受理节奏与提交节流修复

2026-10-09 07:20 的一次真实批次（95 单，4 路并发，读取超时 30s）以及随后四轮
补跑的完整结果（用户按轮次着色统计，含逐单成功位置）：

| 轮次 | 提交 | 成功 | 成功率 | 成功在提交顺序中的位置 |
|---|---|---|---|---|
| 第一轮 | 95 | 33 | 34.7% | 午餐 2,3,4 之后每 3 单 1 单；晚餐 1,4,7,10,13,16 |
| 第二轮 | 62 | 22 | 35.5% | 稳态仍为每 3 单 1 单 |
| 第三轮 | 40 | 15 | 37.5% | 同上 |
| 第四轮 | 25 | 9 | 36.0% | 同上 |
| 第五轮 | 16 | 7 | 43.8% | 同上；另有 9 单五轮均未成功 |

原始日志（07:20:12—07:21:21）：失败请求平均 0.361 秒返回 HTTP 200 + code=500 +
`java.lang.IndexOutOfBoundsException: Index: 0, Size: 0`；成功请求平均约 7.4 秒；
**33 个成功 × 约 2.1 秒 ≈ 69.2 秒 = 本轮实际耗时**——成功几乎严格按平台节奏铺满
全程，而程序在 4 路滚动补位下的发送节奏约为 1.37 单/秒。

结论（与 10-08 现场证据一致）：

1. 平台对同一账号的建单受理上限约 **1 单 / 2.1 秒**；超速请求被快速驳回
   （平台内部异常，空列表取下标 0），且**仍会消耗一个平台订单序列号**——用户
   看到实际订单不到 100 单而序列号已到 200 多（五轮合计 238 次请求 ≈ 238 个
   序列号），失败单即"幽灵订单"（不可见、不产生扣费）。
2. 同一订单首轮失败、次轮成功（payload 相同）：失败与订单内容无关，只与发送
   节奏有关；这也解释了"网页/手机手动下单也失败、而程序单条重试（串行、节奏低）
   立刻成功"。
3. 4 路并发本身不违规，问题在**没有节流**：失败请求 0.36 秒即回、车道立刻补发，
   实际发送节奏被推到约 3 倍于平台上限，于是每轮约 2/3 被驳回、"每 3 单 1 单"
   的节拍由此而来。

### 修复：提交最小间隔（`sss_submit_min_interval_s`）

- 新增配置 `sss_submit_min_interval_s`（秒，出厂 **2.5**，0 = 关闭节流；无界面
  入口，改 `config.json` 生效）。提交器在每次 POST 之前经 `_SubmitPacer` 排队，
  令相邻两次 POST 的起点至少间隔该值；并发路数不变（间隔生效后 4 路最多约
  3 个请求在途，低于平台上限）。
- 出现平台快速驳回特征（HTTP 200 内部异常且含 `IndexOutOfBounds`、耗时 ≤1.5 秒）
  时，间隔按 ×1.5 自动放宽（上限 10 秒）并打印一行提示；只影响节奏，不改变任何
  结果分类与"不自动重发"语义。节流等待期间若出现停止/401/余额不足，请求记为
  "未发送"（它确实没有发出）。
- 可观测：`开始下单：共 N 单，并发 4 路，读取超时 30s，提交最小间隔 2.5s`；
  本轮汇总行追加 `；提交最小间隔 X 秒`；每条诊断记录新增 `min_interval_s`
  字段（该请求发出时生效的间隔）。
- 效果估算：95 单 × 2.5 秒 ≈ 4 分钟，全程低于平台受理上限，预期不再出现批量
  驳回（10-08"单单重试成功"与 10-09 的速率数据都支持这一点）。
- 回退：把 `sss_submit_min_interval_s` 配成 0 即完全关闭节流（恢复旧行为）。

后续取证时，匹配相同 `client_request_id`，比较 `payload_digest`、`wire_digest`、
`auth_context`、`cookie_context`、`workers` 和 `http_status`，即可区分内容变化、
会话变化与并发变化。即使摘要全部相同，仍需平台异常堆栈/事务记录才能锁定服务端原因。
