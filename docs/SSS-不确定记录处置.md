# 闪时送未决记录与阻断处置（3.6.19 起已下线该阻断）

> **一句话**：3.6.19 起不再有「人工核对 + 审计解除才能重跑」的阻断。批量下单结束后
> 若有未确认/失败的单，**直接再运行一次即可补单**——提交前会先做站内只读对账，
> 已存在的订单不会重复提交。本文保留为历史说明与现状速查。

---

## 1. 现在的行为（3.6.19 起）

- 下单结束后仍会如实报告「未确认 / 已发送未知 / 失败」的数量，并给出一句下一步；
  这句下一步现在统一是「可直接再运行一次补单……本批不会自动重发」。
- 提交前的站内对账（按送达日窗口）会把站内已存在的订单标为已确认并跳过提交；
  所以重跑不会因为早期成功单而重复下单。
- 历史上写入的「已发送未知」记录（本地 journal）**仍然保留**：运行开始时会先做一次
  只读对账，站内已出现的记录会被自动标记为 resolved；查不到的记录保持原样、
  **不再阻断**任何后续运行（只打印一行「提示：…本批继续提交」）。
- 记录文件位置（如需人工排查）：作者目录下的 `sss-authoritative-*.json` 系列，
  由 `app/ordering/uncertain.py` 管理；**不要手改或删除**——它们只是排查账本，
  留着不影响重跑。
- **已删除**：`sss_uncertain_records` / `sss_uncertain_resolve` / `start_sss_review`
  三个管理员接口与界面上的「未决记录」面板（含勾选、备注、逐字确认、二次确认）。

## 2. 迁移与回退边界

- 仍保留的并发保护：同一权威 journal + 同一批次 key 的**跨进程提交锁**。两个实例
  同时跑同一批次时，后到的会被拒绝（`blocked_concurrent`），不会双发。
- 不再保留的保护：跨运行去重（依赖「站内能查到」；若平台列表延迟很久，重跑可能
  对同一单再发一次——这是 3.6.19 有意的取舍，见 CHANGELOG）。

## 3. 出问题时的排查入口

- 应用内「闪时送更多工具 → 闪时送诊断日志」：查看 / 复制 / 保存
  `sss-diagnostics/YYYY-MM-DD.jsonl`（脱敏，不含姓名与电话）。
- 现场事实与字段说明见 [SSS-下单失败与重试排查.md](SSS-下单失败与重试排查.md)。
- 版本与回退记录见仓库根目录 [CHANGELOG.md](../CHANGELOG.md)。
