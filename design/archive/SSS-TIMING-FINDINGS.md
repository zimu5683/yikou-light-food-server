# 闪时送下单耗时：实测归因与优化计划（2026-09-10）

> 本文只记录**实测**结论与据此得出的计划，不含未经验证的猜测。
> 所有数字都可用 `tools/` 下的只读探针复现，命令见文末。

## 落地状态（2026-09-13 更新）

### P0 服务端预筛（已实施）

- `app/sss.py`：新增 `_build_list_prefilter()`；`_list_pending_orders` / `_reconcile_tasks`
  支持 `prefilter` 参数（默认 None → 旧行为）；`_safe_reconcile` 负责「预筛 → 缺失/报错则
  无过滤全量复核」，开关 `YIKOU_SSS_SERVER_PREFILTER=0` 可退回全量。
- 生产参数实测（2026-09-11 08:31）：预筛 `09-10~09-12` → **2 页 / 2.8 秒 / 134 条**；
  无过滤全量 8 页即 31.0 秒（全量应为 23 页）；两者交给未改动的 `_reconcile_tasks`
  得到**完全一致**的结论（匹配 65/66、缺失 1、重复 0）。
- 同一预筛查询连打 25 次：**25/25 成功**，中位 1.33s（参数与限流都没问题）。
- **刻意不带 `status` 参数**：2026-09-11 实测「送达日 09-10 的订单全部是 status=3
  （已发单），目标日 09-11 的订单是 status=2」——同一批订单派发后会由 2 变 3，
  硬编码 `status=2` 会把这批订单筛没、误判缺失。`statusList` 无效且 `status` 是单值，
  无法一次查多个状态，因此只按时间窗预筛。

### P0b 预筛健壮性（已实施，由 2026-09-13 真实故障驱动）

2026-09-13 22:53 的真实批次（75 单）出现降级，日志为「服务端预筛查询失败（缺少
records/list）」与「服务端预筛缺少 75 单」。逐项实测结论：

1. **窗口参数本身没错**：该批目标送达日 09-14，生产窗口 `09-13 00:00 ~ 09-15 23:59`；
   查得最新一单 `orderTime = 2026-09-13 22:57:39`，**确实落在窗口内**。
2. **同一窗口 5 分钟后能查到全部订单**（22:59 复测：total=116，含 75 单目标单）
   → 属于**写后可见性延迟**（批次刚创建、列表还读不到），不是参数语义错误。
3. **窗口内真的没有订单时，服务端返回「空壳」**（`{"success":true,"result":{"total":0,...}}`，
   没有 `records` 字段）——实测 08-12 单日、09-14 单日窗口都是这个形状，于是走「查询失败」分支。
4. 兜底逻辑两次都正确兜住了（全量复核判定 0/75 缺失，未误判、未重复下单）。

**修法**：`_safe_reconcile` 增加 `zero_retry_delay`——预筛「窗口内 0 条」时先等 2 秒重查一次，
仍为空才降级全量；这次重查**不占用 attempts 配额**。只挂在**提交后**的对账上
（收尾 / 重试前 / 重试后）；提交前那次不挂——那时站内本就没有本批订单，重查纯属浪费。

### P1 提交阶段：已量出的边界（尚未改动）

用两次真实批次反推（4 路并发）：

| 批次 | 单数 | 提交墙钟 | 吞吐 | 每单服务端耗时 |
| --- | --- | --- | --- | --- |
| 09-10 21:50 | 66 | 138s | 0.48/s | ≈8.4s |
| 09-12 22:13 | 58 | 133s | 0.44/s | ≈9.2s |

对照实测：**非法报文 POST 单次仅 0.24s**（服务端校验即失败，不走建单逻辑）。
并发压测 4/8/16/32 路：无排队、无限流、无 429，吞吐线性到 109/s。
→ 客户端（并发、CPU、连接复用）**不是瓶颈**，真实建单的服务端处理时间才是。
「提高并发能否提速」目前**无法用非法报文证明**，必须在真实批次上量（见 P1 计划）。

对账优化后，一次运行的对账开销从约 95 秒（49+25+21）降到约 3-8 秒，
**提交阶段已占总时长 80% 以上**。

## 一、结论速览

用户看到的两段日志：

```
21:50:45 INFO 开始下单：共 66 单，并发 4 路，读取超时 20s
21:51:34 INFO 下单前站内对账：站内匹配 0/66 单，缺失 66 单，重复 0 单   ← 中间 49 秒
```

**这 49 秒全部花在「订单列表分页扫描」上**：程序在提交任何订单前，会先查一次站内
订单做对账；而它查列表时**没有任何服务端过滤**，等于每次都把账号的全部历史订单
从头翻一遍。

实测该账号：

| 指标 | 实测值 |
| --- | --- |
| 站内订单总数 | **2222 单** |
| 每页条数 | 100（业务固定） |
| 每次对账需要页数 | **23 页**，页与页严格串行 |
| 单页耗时 | 中位 **2.0 秒**（min 1.94 / max 2.39） |
| **单次对账扫描成本** | **≈46 秒** |

这正好解释了 49 秒——它就是一次全量扫描（该调用 `attempts=1`，不可能有重试）。

## 二、302.6 秒都花在哪

| 阶段 | 实测成本 | 证据 |
| --- | --- | --- |
| 开始下单 → 下单前对账 | **≈46-49 秒** | 1 次全量扫描 × 23 页 × 2.0 秒 |
| 66 单提交 | **≈138 秒** | 4 并发下每 10 单 23.3 秒 → 每单约 8.5-9.4 秒 |
| 收尾对账 + 缺失重试 | **≈50-65 秒** | 至少再 1-3 次全量扫描（每次 23 页）+ 0.5s 轮询间隔 |
| 合计 | **302.6 秒** | 与日志一致 |

**一次真实运行里，对账扫描会被执行 5-6 次**（下单前 1 次、收尾 1-3 次、
重试前后各 1-3 次），也就是 115-138 次列表请求。这是最大且最确定的浪费。

## 三、决定性的实测发现：服务端其实支持过滤

代码注释里写着「服务端不接受 startTime/endTime/statusList 过滤参数（2026-09-10 实测）」，
于是退化成全量扫描。本次实测发现**该结论来自参数类型/命名不匹配，而非服务端没有能力**：

- 传字符串日期会被 Spring 的 `BindException` 直接拒绝：
  `orderOneTouchSendListRequest.startTime` 要求 `java.lang.Long`；
- 正确形式是 **epoch 毫秒**：`startTime` / `endTime`；
- 状态参数是 **`status`（单数）**，`statusList` 无效。

实测对比（同一账号、同一时刻）：

| 请求 | total | 首页条数 | 耗时 |
| --- | --- | --- | --- |
| 当前实现（无过滤） | 2222 | 100 | 2.34s |
| `status=2` + `startTime/endTime`（批次窗口，放宽 1 天） | **65** | **65** | **1.27-1.71s** |

### 等价性验证（关键，防止优化引入重复下单）

把两种抓法拿到的记录，分别喂给**现有未改动的** `_reconcile_tasks` 跑对账：

```
A 全量扫描：匹配 65/66，缺失 1，重复 0；实际取页 11 次，21.5s
B 过滤预筛：匹配 65/66，缺失 1，重复 0；实际取页  1 次， 1.7s
结论：两份记录的对账结果完全一致 ✅
```

（这次两边都缺 1 单，是因为该单当时确实还没落到站内；两种策略对此判断一致。）

**因此：单次对账可以从 23 页 / 46 秒降到 1 页 / 1.7 秒，约 30 倍。**

## 四、另外一个反直觉的实测结果

用**真实报文形状**（取自 Excel 的真实 payload，仅把 `storeId` 换成不存在的门店号，
服务端必然校验失败、不会建单）测下单接口：

```
并发 1/4/8 路：单次 0.24-0.28s，服务端 0.26s 内就返回错误
```

也就是说：**下单接口本身在这条链路上并不慢**（网络、TLS、代理、客户端都没有
8-10 秒的固有开销；列表页请求同样稳定在 2 秒）。真实下单每单 8.5-9.4 秒，
只能来自**服务端「建单成功」这条分支内部的处理**（第三方配送派单、门店校验等），
或者平台对该账号的建单接口有节流。

这一条**目前证据不足以定论**，必须用真实批次量一次（见计划 P1）。

## 五、优化计划（按“收益/风险”排序）

### P0 — 对账改为「服务端预筛 + 本地精筛」（✅ 已实施，收益最大）

- 改动点：`_list_pending_orders`（app/sss.py:1080 起）的查询参数。
- 做法：用目标批次日期推出 `startTime/endTime`（epoch 毫秒，**往前后各放宽 1 天**
  作为安全边界），加 `status=2`；**本地按送达日 + 状态的过滤逻辑一行都不删**，
  服务端只做粗筛，权威判定仍然是本地过滤。
- 预期：单次对账 46 秒 → 1.7 秒；一次运行总耗时预计从 302 秒降到 **约 120-150 秒**。
- 风险与兜底：
  1. 过滤窗口边界若比订单创建时间窄，会把订单判成「缺失」→ 现有 fail-closed
     逻辑不会重复提交，只会停下来；
  2. 但这会破坏体验，所以必须加兜底：**若预筛后仍判定「有缺失」，先做一次
     无过滤的全量扫描复核**，确认确实缺失再走原有停止/重试流程；
  3. 过滤参数一律由程序内部按日期计算，不暴露给用户，避免配错；
  4. 需要重新测一次 `attempts` 轮询次数——扫描变便宜后，轮询等待策略也应重估。

### P1 — 先加埋点，量出真实下单每单耗时（已就位，零风险）

已在 `app/sss.py` 增加默认关闭的埋点（见“附：本次代码改动”），
`YIKOU_SSS_TRACE=1` 时按行输出：

```
[sss-trace 21:51:02] list page 1: 2.01s 返回 100 条 total=2221
[sss-trace 21:51:04] list sweep 结束：23 页 46.2s，命中目标日 65 条
[sss-trace 21:51:56] POST 第 3 行 椰耶耶: 8.42s -> success
```

用它就能确认：若真实 POST 稳定 8 秒以上而探针只有 0.26 秒，说明瓶颈在服务端建单
分支，客户端怎么改都没用；此时可选的提速手段是：
- 提高并发（`sss_max_workers`，当前 4；上限 20）——**需先确认平台没有按账号限流**，
  否则会触发风控或产生「不确定」订单；
- 适当加大 `sss_read_timeout_s`，避免慢响应被误判为 uncertain；
- 若平台对同一账号串行建单，则并发无效，只能接受这个下限或与平台侧沟通。

### P2 — 对账循环里的重复开销

1. **每轮重试都会重建 Session**：`submit_round` 每次都 `submit_factory()` → 4 个
   `fork()` → 4 次新 TLS 握手。按实测握手量级每次约 0.1-0.3 秒，多轮时是纯浪费。
2. **轮询间隔与次数**：`_RECONCILE_POLL_ATTEMPTS=3` + 0.5 秒间隔，
   在“每次扫描 46 秒”的前提下几乎不起作用；P0 生效后需要重新设计
   （例如首轮快查 1 页，缺失时再等待数秒做一次全量复核）。
3. `pageSize` 不要盲目调大：实测 `pageSize=1000` 单页要 **17.9 秒 / 1.9MB**，
   比 10 页 × 2 秒更慢。

### P3 — 记录已知但不紧急的隐患

- 站内订单超过 10000 单时，每次扫描会在 100 页上限处抛错（当前 2222 单，尚有空间）；
- `_INACTIVE_ORDER_STATUS` 为空集，所有状态都算“活跃”，本地过滤形同虚设——
  这也是全量扫描显得“必要”的原因之一，P0 正好绕过它。
