# 闪时送：对账提速与下单并发（2026-09-26 实测驱动）

> 本文记录 **3.6.15** 的对账/并发改动与后续的出厂并发回落（§3.7，v2 起 4 路）：
> 诊断证据、设计取舍、实测数字与回退办法。
> 取代 `design/archive/SSS-TIMING-FINDINGS.md` 里「对账 = 窗口预筛 + 全量复核」的旧结论
> （归档文件按规则不改，保留为历史）。

## 1. 现象：提交前对账白扫 69 秒

2026-09-26 23:08 的一次真实批次（35 单，目标送达日 09-27）日志时间线：

```
23:08:19 INFO 开始下单：共 35 单，并发 4 路，读取超时 20s
23:08:19 INFO 下单前站内对账：服务端预筛查询失败（订单列表响应缺少 records/list
              （服务端可能不支持本次查询参数或结构已变化），为避免重复下单已停止），
              正在用无过滤全量扫描复核
23:09:28 INFO 下单前站内对账：站内匹配 0/35 单，缺失 35 单，重复 0 单
```

中间 **69 秒**全部花在「无过滤全量扫描」上：账号历史订单约 3000 单（09-13 实测 2395，
按每天约 44 单增长），每页 100 条、单页约 2 秒，30+ 页串行翻完。

链路（改动前的代码）：

1. 提交前对账用「目标送达日 ±1 天」的时间窗查站内订单。提交前站内本来就没有本批订单，
   窗口是空的；服务端对空结果返回 **空壳**：`{"success":true,"result":{"total":0,...,"pages":0}}`（无 `records`）。
2. `_list_records` 把空壳当结构异常抛错 → 这次查询被判「查询失败」。
3. `_safe_reconcile` 见预筛失败/有缺失就退回 **无过滤全量扫描**（`reconcile.py` 旧 559-575 行）。
4. 即使修好空壳，「预筛有缺失 → 全量复核」在提交前也**必然触发**（0 匹配、35 单全缺），
   于是每次下单都要白扫一遍全量历史。

## 3. 改动

### 3.1 空壳 = 空页（`reconcile._is_empty_shell`）

`total` 明确为 0、又没有 `records`/`list` → 返回 `([], 0)`（并 `_trace` 原始报文）。
缺 `total`、`total>0`、`total` 读不出来的空壳**仍然 fail-closed**。

### 3.2 删掉「无过滤全量扫描复核」，换成只读的「时间窗自检」

**为什么敢删**：全量扫描唯一被证明有效的作用是绕开上面的空壳 bug；对账判定本身是
「服务端粗筛 + 本地严格判定」，全量扫描只多取记录、不改判定。两类真实故障它也救不了：

- 写后可见性延迟：全量扫描同样查不到（P0b 实测）；
- 预约送达日被平台改期：本地按送达日过滤会把它筛掉，需要的是姓名+电话宽窗复核
  （`_reconcile_person_matches`，管理员「只读核对」按钮），不是更大的抓取窗口。

**替代安全网**（`_verify_list_window`，只在「预筛生效 + 查询成功 + 匹配数为 0」时执行，
结论按进程缓存 `_WINDOW_CHECK_TTL_S=600` 秒）：

1. 探针 A：无过滤 `pageSize=1` 取最新 1 条（列表最新在前，见 §2）；
2. 探针 B：用这条记录的**创建时间 ±1 天**做时间窗再查 1 条——该窗口按构造必然包含它；
3. 探针 B 有记录 → `ok`；探针 A 也没有记录（账号没有订单）→ `ok`；
   探针 B 空而探针 A 有记录 → `unsupported` → **本次对账 return None，整批停止，绝不提交**；
   请求异常/创建时间读不出 → `inconclusive`（不阻断，只记一行日志）。

判据不会误停：只有「账号确实有订单、而必然包含它的窗口却查不到」才判 `unsupported`。
自检**不依赖列表排序**：无论探针 A 取到哪一条订单，它自己的创建时间必然落在「它 ±1 天」
的窗口内，所以「探针 B 空」只可能是时间窗没被服务端接受。

### 3.3 窗口查询用更大的页（`_WINDOW_PAGE_SIZE=300`）

窗口内 100-140 条 → 1 页 ≈ 1.9 秒（原来是 2 页 ≈ 2.8 秒）。无过滤路径保持
`_LIST_PAGE_SIZE=100`：`pageSize=1000` 实测 17.9 秒 / 1.9MB，盲目放大会更慢。

### 3.4 宽窗只读核对也走窗口

`_reconcile_person_matches`（管理员「只读核对站内订单」，姓名+电话 ±3 天）原本完全没有过滤
条件，同样每次翻全量历史；现在传 `prefilter=_build_list_prefilter(tasks, margin=days_margin)`。
**本地 ±margin 天的判定一字未改**（服务端窗口只做粗筛）。

### 3.5 并发 4 → 8、读取超时 20 → 30 秒（一次性迁移）

`sss_max_workers` / `sss_read_timeout_s` 界面上从来没有入口，旧配置里保存的只可能是旧出厂
默认；只改默认值对已有安装无效。因此新增配置字段 `defaults_revision`（旧文件缺键 = 0），
`AppConfig` 在 `revision < DEFAULTS_REVISION` 时做**一次性**迁移：仅当取值仍等于旧出厂默认
（4 / 20.0）时改为新默认（8 / 30.0）；显式改过的其它值（1 = 串行回退、2、6、12、20…）不动。

- 并发依据：见 §2（吞吐 = 并发 ÷ 每单耗时，4 路实测完全吻合）。
- 超时依据：并发翻倍后若平台在建单上排队，单请求耗时会上升，而超时会被归类「已发送未知」
  并要求人工只读核对；30 秒留余量（仍远低于 120 秒上限）。
- 可观测：每轮提交后新增一行 `本轮提交 N 单，耗时 X 秒，每单平均 Y 秒（吞吐 Z 单/秒）`，
  均时接近读取超时 60% 时附一句「把并发调低 / 把读取超时调高」。

### 3.6 对账轮询重估

单次对账从 69 秒降到约 2 秒后，复查变便宜：`_RECONCILE_POLL_ATTEMPTS` 3 → 4、
`_RECONCILE_POLL_INTERVAL_S` 0.5 → 2.0（提交后对账最坏多等约 4.5 秒），
换取「刚写入、列表还没读到」的短延迟场景不再被判「未确认」。全程只读，绝不重发 POST。

### 3.7 出厂并发回落到 4 路（v1 → v2）

出厂默认从 8 路回到 **4 路**，与桌面版（`yikou-light-food-desktop`，v3.6.1 起）口径一致：
`DEFAULTS_REVISION` 1 → 2，迁移规则不变 —— 仅当 `sss_max_workers` 仍等于上一代出厂默认（8）
时搬到 4；用户显式改过的其它取值（1 = 串行回退、2、6、12、20…）原样保留，
`sss_read_timeout_s` 30 秒不变。

- 依据：吞吐 = 并发 ÷ 每单耗时（§2 的 4 路实测完全吻合），4 路已在这条线性区；
  继续翻倍的收益有限，而更低并发在平台偶发排队/限流时留下的余量更大。并发只影响
  「同时在建的单数」，不改变「至少一次提交 + 站内只读对账确认」的兜底语义。
- 取值仍可配置：`sss_max_workers`（无界面入口，改 `config.json` 后重启生效），上限 20；
  配置对象缺字段或取值不可解析时按**串行 1 路**保守回退
  （`app/ordering/runner.py::resolve_create_workers`）。

## 4. 效果（预估 vs 实测）

| 环节 | 改动前 | 改动后（预估） |
|---|---|---|
| 提交前对账 | 69 秒（全量扫描） | 约 2 秒（1 页窗口）+ 约 2-4 秒（首次时间窗自检，按进程缓存） |
| 收尾对账 | 69 秒 × 1-3 次 | 约 2-4 秒/次 |
| 管理员宽窗复核 | 69 秒+ | 约 4 页 / 8 秒（±3 天窗口，`pageSize=300`） |
| 35 单提交 | 约 73 秒（4 路） | 约 37 秒（8 路，前提：平台不排队）；出厂回到 4 路后按 4 路估算 |
| 整轮 | 约 220 秒+ | 约 55-70 秒 |

**并发收益必须在真实批次上复核**：`concurrency_out.txt` 压的是「校验失败」分支，
真实建单路径的排队行为只能用生产批次验证（看汇总行的每单均时）。

## 5. 被否方案（与理由）

- **分页并发抓取**：窗口化后每轮只需 1-2 页，收益消失；并行翻页会引入偏移漂移、
  重复页 fail-closed 误触发、对服务端施压等新风险。
- **保留「缺失 → 更宽窗口复核」**：本批订单的创建时间必然落在窗口内（窗口以本批目标送达日为
  中心，程序只在送达日前一天晚上创建），更宽的抓取窗口救不了任何已知故障，只是每次多花 4-12 秒。
- **自适应并发 / 并发界面入口**：前端契约与浏览器门禁成本高，本次靠出厂默认 + 迁移生效。
- **`pageSize` 全局放大**：见 §3.3。

## 6. 回退办法

- 时间窗出问题：`YIKOU_SSS_SERVER_PREFILTER=0` → 退回无过滤扫描（旧行为，慢但可用）。
- 并发/超时：改配置 `sss_max_workers` / `sss_read_timeout_s`（界面暂无入口）；
  迁移只搬旧出厂默认，改过的值不会被覆盖。
- 提交节奏：`sss_submit_min_interval_s`（秒，出厂 2.5，0 = 关闭节流）。平台建单
  受理上限约 1 单 / 2.1 秒（2026-10-09 实测）；越线会出现"每 3 单成功 1 单"式
  批量驳回并消耗平台序列号。
- 时间窗自检缓存：进程内 `_WINDOW_CHECK_CACHE`，TTL 600 秒；重启进程即清空。

## 7. 验证与复现

```bash
python -m pytest -q                       # 全量门禁
python -m pytest tests/test_sss.py -q     # 对账/提交重点用例
```

只读真机验证（零 POST）：用界面「预检」模式跑一次，日志应满足：

1. 出现一次「时间窗自检：服务端接受 startTime/endTime（…）」；
2. 「预检站内对账：站内匹配 X/Y 单」与登录完成的时间差 ≤ 6 秒；
3. 不再出现「正在用无过滤全量扫描复核」。

真实批次验证：`开始下单：共 N 单，并发 4 路，读取超时 30s，提交最小间隔 2.5s`
（节流默认开启，见 §6）+ 汇总行的每单均时仍接近 8-10 秒、且不再出现成批的
`IndexOutOfBoundsException` 快速驳回（若出现 → 平台受理节奏又收紧，节流会自动
放宽间隔并打日志）。
