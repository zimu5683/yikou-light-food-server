## 3. 目标日期规则

网站 21:00 截止（有时 20:00），程序总在 21:00 后运行：

- 运行时刻在 **20:00 ~ 次日 10:00** → 目标日期 = **运行日 + 1 天**
- 其它时刻 → 目标日期 = **运行日**
- 可在配置里调整窗口边界（`wps_target_hour_start` / `wps_target_hour_end`）

日期列定位：**只比对「月.日」，忽略星期文字**
（实测发现协作者把 `9.16` 写成了「9.16周一」，但 2026-09-16 是周三 → 认星期会找错列）。

## 4. 写入规则

对每个本地子表的每一行：

```
在云端按【名字 + 电话】找人（两者都相同才算同一人）

旧客户：目标日期格 = 1
        总餐次 += (本地「餐次」 − 账本里上次已同步的「餐次」)

新客户：追加一行，填 名字/地址/电话/类型/餐种/总餐次(=本地餐次)/目标日期格(=1)
        其它日期格留空、备注不写、已出餐/剩余餐 由协作者公式负责

通讯记号：备注列右边第 2 列 = 周几数字（周日1、周一2 … 周六7）
         测试模式下不写
```

### 幂等（防止重复跑翻倍）

本地账本 `wps_sync_state.json`（用户配置目录）记录每人上次已同步的「餐次」值：

| 场景 | 本地餐次 | 账本值 | 本次加 |
|---|---|---|---|
| 首次下单 1 餐 | 1 | 无 | +1 |
| 加餐到 3 餐 | 3 | 1 | +2 |
| 重复跑（仍是 3） | 3 | 3 | 0（不写） |
| 退单变少 | 1 | 3 | **负数 → 跳过 + 记日志**（不自动回退） |

## 5. 容错红线

1. 找不到目标日期列 → 不写、不建列，提示"请确认协作者是否已加今天的列"
2. 差额为负 → 跳过该人，记日志
3. 测试模式缺 file_id → 提示，不写
4. 任何异常 → 只记日志，**绝不阻塞本地排单任务**
5. 写入后回读校验（读回目标格确认 = 1），失败则报告并不更新账本

### 与初版计划的差异（实施中修正）

1. **总餐次语义**：一开始按"云端 + 本地"累加实现，核对真实数据后确认应当是
   **写成与本地一致的绝对值**——本地表就是网站当前的完整状态。
   绝对值写法天然幂等：重复上传零副作用（用户确认"12 餐肯定是多的，他只下了 6 餐"）。
2. **测试模式**：从"单一测试文件"改为**每张正式表各自对应一个测试副本**
   （`测试-东湖中餐.xlsx` 等），否则 6 张表会写进同一个文件互相追加。
3. **回读校验**：初版只抽查首尾行，实测发现"恰好末尾行原本就是 1"会造成假阳性；
   改为**逐格核对**目标列与总餐次。
4. **通讯记号**位置确认为「备注列右侧第 2 列」，6 张表一致（实测）。
5. **列定位容错**：实测发现协作者把 `9.16` 写成「9.16周一」（实际是周三），
   因此日期列**只比对月.日**；工作列表头也不统一（`总餐次/总餐数`、`已出餐/出餐`），
   一律按名字找列，不按列号推算。

## 修复记录（2026-09-11 下午，由用户复核发现）

用户在云端核对测试表时发现两个问题，均已修复：

### 缺陷 1：新客户追加行缺少「类型」「餐种」

**现象**：追加的新客户行只有姓名/地址/电话 + 日期格，`类型`/`餐种` 是空的
（表格里出现"类型空白但餐种=经济"的怪行）。

**原因**：`apply_plan` 构造新客户行时只写了 name/address/phone，
`Change` 里也没有携带本地读到的 `meal_type`/`meal_kind`。

**修复**：
- `Change` 增加 `address` / `meal_type` / `meal_kind` 字段；
- `plan.columns` 增加 `type` / `kind`（按表头名查找）；
- 追加行时一并写入类型、餐种；
- 新增测试 `test_new_customer_row_is_complete` 锁定行为。

### 缺陷 2：往被改乱表头的表里写入（防护缺失）

**现象**：开发期间为了模拟"协作者加列"，插入列失败后误把 `9.12 周六`
写进了 `类型` 列（覆盖了表头），之后程序仍往那一列写数字。

**修复**：
- 表头解析后做**结构性校验**：读不出 `姓名/电话/类型/餐种/总餐次` 中
  任何一项就拒绝写入，只给出"云端表头异常"提示；
- `read_grid` 在接口没返回 `detail`（表不可读/非在线表格）时抛错，
  而不是返回空结果（否则会把"读不了"误判成"表是空的"）；
- 新增测试 `test_broken_header_blocks_write`。

**已确认 6 张正式表的这些表头都存在**，因此该防护不会误拦正式表。

## ⚠ 接口每日限流（2026-09-11 22:00 实测）

### 现象

开发过程中反复调用云端接口，触发了金山侧的**每日调用上限**：

```
code 429001  今日调用次数已达上限，将于 2026-09-12 08:00:00 恢复
code 429002  频繁触发调用限制，将于 2026-09-12 08:00:00 恢复
```

**所有操作全部受限**：读表格内容、写单元格、列文件、搜索文件、取分享链接。
授权状态查询（读系统密钥链）不受影响。

### 影响

- **当天无法再做任何云端操作**，包括程序的预览与上传；
- 用户搜不到第 6 个「基准-衣锦中餐.xlsx」，正是搜索接口被限流所致
  （该文件创建时 rename 返回 `code=0`，记录在 `design/WPS基线存档.json`）；
- 本地排单任务**完全不受影响**。

### 已做的改进

`KdocsCli._run` 现在识别 429001/429002，抛出可读提示：

> 今日云文档调用额度已用尽（金山接口限流），约 N 小时 M 分钟后恢复。
> 这不是程序故障：读表、写表、搜索都会受限，本地排单任务不受影响。

界面预览/上传失败时会直接显示这句，而不是含糊的 `code=429001`。

> 注：接口返回的 `reset_at` 时区口径不稳定（实测与提示文案相差 8 小时），
> 所以只显示"还有多久"，不显示具体时点。

### 省额度约定（后续开发注意）

构建/调试时应避免重复全量扫描：
- 一次预览会读 6 张表的表头+全量姓名与工作列，属于**多次**调用；
- 对齐副本、生成快照、取链接都会各消耗多次调用；
- 建议：批量验证合并成一次脚本跑完，不要反复零散调用；
- 额度恢复时间固定为**每日 08:00**。

## 真机测试暴露的两个缺陷及修复（2026-09-12）

用户用部署版实测，截图显示两个问题，均已定位并修复：

### 缺陷 3：单次写入超过接口上限 → 整张表写入失败

**现象**（日志）：
```
[云同步] 东湖中餐 写入失败：云文档接口返回 code=400001:
        rangeData length 175 exceed...ds limit 100
[云同步] 完成：更新 0 人、新增 29 人、已完成 0 人；成功 2 张表，失败 1 张
```

**原因**：`KdocsCli.write_cells` 把所有单元格塞进**一次** `update-range-data` 请求，
而该接口单次 `rangeData` 上限是 **100** 项。东湖中餐一次追加 25 人 ≈ 175 格，必然超限。

**修复**：
- `write_cells` 按 `WRITE_BATCH_CELLS = 80` 自动分批（留余量，不贴上限）；
- 新增回归测试 `test_write_cells_batches_under_api_limit`（25 人 × 7 格 = 175 格，断言拆成多批且每批 ≤100）。

**验证**：修复后重跑上传 → `东湖中餐：25 人` 成功、`失败 0 张`。

### 缺陷 4：部分失败被汇总掩盖

**现象**：日志先写"新增 29 人"，末尾才写"成功 2 张表，失败 1 张"，
用户容易误以为整体成功（截图里就是"上传失败，详见日志"与"新增 29 人"并列，观感矛盾）。

**修复**：`wps_upload` 现在**逐表输出结果**并用 OK/ERROR 分级：
```
[OK]    [云同步] ✔ 东湖中餐：25 人
[ERROR] [云同步] ✘ 东湖中餐：写入后回读校验未通过（...）
[WARN]  [云同步] — 东湖晚餐：未找到目标日期列     ← 正常状态，不再是 WARN 噪音
```
返回值新增 `failed_sheets` 与 `reason`，界面可直接显示"以下表写入失败：X、Y"。

### 顺带修复：列号坐标混淆

调试脚本反复把 `read_grid` 的 `(行, 列)` 元组键当成列号用（踩了 3 次）。
为此在 `KdocsCli` 上新增两个便捷方法，从源头避免：
- `read_row(file_id, ws, row)` → `{0-based 列: 文本}`（行号为 1-based）
- `find_column(file_id, ws, names)` → **1-based** 列号

### 夹具告诉我们的规格（全部按目标表逐格反推）

1. **新客户不是表尾追加，而是插入到「地址组」末尾**（这就是用户说的"排序"）：
   黄→「小」组末（r12）、大西 7 人→r34-40、陈章依→「b2」组末（r44）……
   嗯哼→「图书馆」组末（r123，nono 之后、哒哒 之前）。
2. 老客户零变化（本轮 25 个订单全是新客户）。
3. 新行值：名字/地址/电话/类型/餐种/总餐次 + 目标日期格=1；
   L/M（已出餐/剩余餐）在目标表导出里是拍平的公式值，程序不写。
4. 新行底色：经济 = A~J 白、K~M 金黄、N 白（照抄模板行「哒哒」r99）；
   **豪华 = 名字到备注整段金黄（A~M，用户口头确认"整行金黄"，含 N）**。
   注：目标表导出里豪华行 N 列未涂色，以用户 2026-09-12 的确认为准（程序涂 N）。
5. 地址组匹配：大小写不敏感（本地「B2」= 云端「b2」，落表按本地原样写）；
   「小西」→「小」是协作者的写法映射（ADDRESS_ALIASES 显式别名，落表写「小」）。
6. 通讯记号：位于备注右侧**第一个 1~7 数字格**（东湖中餐实测在 Q 列 = 备注+3，
   不是早前记录的备注+2，会动！）；值 = **运行日**的周几（周五晚跑记 6，
   不是目标日期周六的 7）—— 基线记号 5（周四跑）→ 目标 6（周五跑）可证。
7. 组内顺序：经济在前、豪华在后（各自保持本地顺序）。目标表 D2 组的
   灵/刘姵怡顺序与该规则有一处相邻互换（数据完全相同，视为手工录入顺序差异）。

### 代码改动（app/wps_cloud.py，已全部离线验证）

- `InsertBlock` + `plan.insert_blocks`：新客户按地址组分块，块升序、
  块内经济在前；老客户写入行号补插入位移（插行会让下方内容下移）。
- `KdocsCli.insert_rows()`：`insert-rows-cols`（0-based 闭区间）；
  表尾追加块**不调**插入接口（写格自动扩表）。
- `KdocsCli.delete_rows()` + `_rollback_inserts()`：插入成功但写入失败时
  回滚插出的行，云端不留烂尾空行。
- `find_marker_column()`：备注右侧找 1~7 数字格定位记号位，兜底备注+2。
- `build_plan(run_date=)`：记号值 = 运行日周几；bridge 传 `date.today()`。
- `build_format_ops()`：所有新行格式压成**区间合并**的 format 操作
  （相邻同色列合并、相邻行合并），25 个新行 ≈ 32 个操作、1 次调用
  （旧实现逐行 copy_row_format 要 25 次）。`copy_row_format` 已删除。
- `apply_plan`：先插行（升序）→ 写格 → 格式 → 回读校验；失败回滚插行。
